# Random merchant requests — 2026-10-04

User approved randomized needs on new visits. Each actual scheduled arrival (days 1, 4, 7, ...) now uniformly chooses one or two distinct goods from the existing eligible pool. Selected wood quantity is 3–6, sun-dried mudbrick quantity is 10–20, both inclusive. Each count/item/quantity choice uses the ledger's own RNG. Prices, offered stock, budget and visit timing are unchanged. This is provisional configuration. A visit can request only bricks or only wood; consecutive visits may legitimately repeat. No guarantee of a buyer for every owned resource.

Rolls occur only in the new-arrival branch, not on ordinary days/ticks or menu creation. The existing session runtime host retains selected requests and remaining demand over view/map reloads. Sold units consume demand; buyback does not refill it. Sell hides unselected goods and authoritative trades reject them. Configuration validates count bounds and optional quantity_min against existing quantity maxima. Fixed-request mode remains available for deterministic accounting tests. This is session-only continuity, not disk saving or city-stat-driven tier selection.

Validation: new MerchantRandomRequestsTest covers 20 seeded actual visits, quantity/pool/count bounds, Sell row filtering, real sell/buyback accounting, excluded goods, minute stability, panel reopen, main-map recreation, rewind and non-visit days. Seed 20261004 produced 15 distinct profiles; first three were day 1 wood 5, day 4 wood 3 + bricks 10, day 7 bricks 18. These are test examples, not predetermined gameplay outcomes. The test supplies bounded inventory/funds for quota assertions.

Godot 4.5.2 import and final runs passed: random-requests graphical suite plus merchant state, access, production and main-map accounting regressions. Existing accounting fixtures explicitly disable randomization in their process so prior exact totals remain reproducible; the new suite tests production randomization enabled. First three visit screenshots inspected at 400x225 logical resolution. No script errors in final runs; only the expected virtual-display VSync warning. A stale engine process from an earlier interrupted test caused temporary debug-port conflicts and was terminated before final verification.

Earlier reports with fixed six-wood/twenty-brick requests describe the previous version and fixed regression scenario. Production now uses randomized requests from the first visit onward.
